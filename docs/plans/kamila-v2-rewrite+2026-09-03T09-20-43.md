## 2. Why this is a SEPARATE plan (decision)

- The user explicitly chose: **"Plan the rewrite as a separate doc"** — record the rewrite path
  without touching current code.
- Incremental Quick Wins already live in `code-review-impl` (WS-1..WS-7) and are the **low-risk
  path to keep today's Kamila reliable**.
- The rewrite is a **4-6 week architectural reset** — a fork/parallel codebase, not a refactor of
  `server.js`. It should stay green-field to avoid dragging in monolith debt.

**Sequencing proposal (for when rewrite is greenlit):**
1. Finish `code-review-impl` Quick Wins on the current bot (keeps it runnable during rebuild).
2. Bootstrap `kamila-v2/` as a **sibling repo** (not replacing `server.js` in place).
3. Port forward, feature-by-feature, cutting over only when parity + tests are met.

## 4. Target architecture (`kamila-v2/`, sibling repo)

Adopt the review's proposed structure **filtered through "keep whatever Kamila actually needs."**
Kamila's core value is **local-first, single-user, Ollama-driven companionship** — many Levanter
features (multi-session, 60 plugins, media downloaders, i18n, anti-link) are scope-creep for a
single-PC bot. Only lift what provides real value.

```
kamila-v2/
├── index.js                 # Entry (Levanter-style bootstrap)
├── config/
│   ├── index.js             # Config loader + validation (.env). Keep API_KEY, WHITELIST, etc.
│   └── schema.js            # Validation (JS-friendly; JSON schema or hand-rolled, not Zod if no-dep)
├── db/
│   ├── index.js             # Database init + connection (better-sqlite3 kept OR Sequelize if)
│   ├── migrations/          # Numbered migrations (implement a tiny migration runner — no dep)
│   └── repositories/        # ContactRepo, MessageRepo, TaskRepo (encapsulate SQL)
├── whatsapp/
│   ├── client.js            # Either whatsapp-web.js (local-first, no Chromium concern) OR Baileys
│   ├── auth.js              # QR + pairing code
│   └── presence.js          # Typing/recording simulation (typing selector already in Kamila)
├── ai/
│   ├── ollama.js            # Caller + CircuitBreaker (port from WS-7)
│   ├── router.js            # Provider selection (Ollama primary; optional Gemini/Groq later)
│   ├── fallback.js          # Cached/degraded replies when Ollama down
│   └── prompts.js           # Prompt templates (persona lives here)
├── state/
│   ├── botState.js          # EventEmitter state (connection, tasks, stats)
│   ├── messageQueue.js      # Outbound priority queue + per-chat rate limits
│   └── sessionManager.js    # Conversation memory per chat (TTL)
├── api/
│   ├── routes/              # REST endpoints (mirror current /api/* + /health + /api/enhance)
│   ├── middleware/          # Auth (API_KEY header-only), validation
│   └── sse.js               # Fixed SSE with heartbeat (port of WS-2) + max-conn cap
├── admin/
│   ├── index.js             # Admin panel SPA entry
│   └── public/              # Modular JS views (overview/chats/tasks/settings/broadcast)
├── jobs/
│   └── tasks.js             # Scheduled/broadcast tasks
└── utils/
    ├── logger.js            # Pino (levels, pretty in dev, rotation) OR keep minimal
    ├── helpers.js           # sanitize*, splitMessage, normalizePhone, parseVCard
    └── validators.js        # Broadcast/number validation
```

**Deliberate omissions (scope-creep the review pushes but Kamila doesn't need):**
multi-session, 60+ plugins, media downloaders (ffmpeg/YT/TikTok), group moderation
(anti-link/anti-word/warn), i18n (11 languages), cloud deploy targets, calendar/GDrive/copilot.

## 5. Phased implementation plan (only when greenlit)

> Each phase ends runnable. Keep the old bot running until Phase 5 cutover.

**Phase 0 — Bootstrap (0.5 wk):** sibling `kamila-v2/` repo, `npm init`, `config/`, `utils/helpers`
port (from `src/lib.js` that WS-6 produces). Port tests.

**Phase 1 — Backend core (1.5 wk):** `db/` + migrations (port current schema: contacts, messages,
evaluations, drafts, tasks, broadcasts, access, stats), repositories, `state/` botState + queue.

**Phase 2 — AI + WhatsApp (1 wk):** port `ai/` (Ollama + circuit breaker + fallback), `whatsapp/`
client (QR + pairing), presence. Wire message → AI → reply pipeline with concurrency limits.

**Phase 3 — API + SSE (1 wk):** port all `/api/*` + `/health`, SSE heartbeat, API_KEY
header-only auth, validation.

**Phase 4 — Admin SPA (1.5 wk):** modular dashboard frontend, current CSS/UX preserved.

**Phase 5 — Parity + cutover (1 wk):** feature-vs-feature diff against current bot, E2E smoke,
cutover. Optionally PM2 to keep it alive.

**Estimated total:** ~5-7 weeks. Trim by dropping Phase 0-4 features already deemed out-of-scope.
